# Episode 106: How Browsers Really Parse HTML (and What That Means for SEO)

Разбор выпуска *Search Off the Record* с Martin Splitt и Gary Illyes: почему HTML нельзя «просто распарсить regex’ом», как браузер закрывает `<head>`, куда класть metadata для Search и что из performance-hints реально влияет на SEO.

---

## Почему парсинг HTML — боль

HTML в теории — структурированный язык. На практике — толерантный хаос: браузеры принимают почти всё, разработчики привыкают писать «как получится», и любой самодельный regex-парсер рано или поздно ломается.

Living Standard специально описывает, как user agents должны обращаться с уже существующим вебом: минимум поломок, максимум совместимости. Валидатор W3C раньше казался священным (эпоха Netscape / IE / star-hack). Сейчас **валидность сама по себе почти не решает** ни для браузеров, ни для поисковиков — пока вы не делаете что-то действительно странное.

Нюанс: «не важно» ≠ «можно ломать как угодно». Есть отклонения, которые меняют ожидания парсера и ломают SEO-сигналы.

---

## Как браузер решает, что `<head>` закончился

Metadata (то, что не показывают пользователю) живёт в контексте metadata — practically это `<head>`.

Если в `<head>` появляется то, чего там быть не должно (например, `<p>`), браузер считает: начался контент для пользователя → автоматически открывает `<body>` и «закрывает» head.

Следствие для Search: теги, которые должны были остаться в head, могут оказаться в body — и инфраструктура Google их **корректно игнорирует**.

### Кейс: hreflang «съеден» скриптом

В video/кейсе с Bastian Grim:

1. В `<head>` были `link rel="hreflang"` — на своём месте.
2. Перед ними стоял `<script>` (в head это легитимно).
3. Скрипт после себя инжектил `<iframe>`.
4. Парсер закрыл head → hreflang уехал в body.
5. Google эти link’и не учёл.

Итог: markup «в исходнике вроде в head», а после разбора — уже нет.

## Что можно в head / body по смыслу спеки

| Элемент | Ожидание |
| --- | --- |
| `meta name="robots"`, charset и т.п. | В контексте metadata → practically **только head** |
| `link` как metadata (`canonical`, `hreflang`…) | Ожидаются в **head** |
| `link` в body | Допустимы в узких случаях (itemprop / определённые `rel`, stylesheet, preload/prefetch, исторический pingback и т.п.) |

Общий принцип выпуска: **metadata-сигналы для поисковиков держите в head**. В body это опасно и неоднозначно.

Почему Search не хочет принимать `rel=canonical` из body «как попало»:

- комментарий / XSS / неэкранированный HTML → чужой canonical угоняет страницу;
- проще вредоносный `<link>`, чем тащить целый `<script>` (хотя JS тоже может дописать canonical в head).

На injected-via-JS canonical Google **не может** просто сказать «никогда не принимаем»: есть легитимные кейсы. Но mixed signals (один canonical в raw HTML, другой после render) — головная боль. Официальный совет: **не менять canonical JavaScript’ом**, если можно избежать; если только так получается — ок, но ясность намерения страдает.

## Стандарт ≠ все правила потребителя HTML

Спека говорит, как работать с HTML-документом. Поверх неё у браузеров и у Search свои application-specific правила.

Браузеры, например:

- на `<script>` (без async/defer) могут остановить разбор, выполнить JS, продолжить;
- делают preliminary scan за ресурсами (картинки), качают в фоне;
- строят DOM/render tree **потоково**, а не «сначала весь HTML, потом экран».

Это поведение спекой полностью не расписано — так устроены браузеры.

Search ближе к браузерам, чем к наивному regex, но:

- не всё браузерное поведение им нужно;
- часть решений жёстче из‑за spam/abuse.

## Prefetch / preload / preconnect и SEO

Hints вроде `dns-prefetch`, `preconnect`, `preload`, `prefetch`, `script async/defer` сильно помогают **пользователям** (особенно на слабом канале и дальних RTT). Gary вспоминает, как preload первых результатов выдачи казался «магией».

Для самого Google как потребителя документа польза часто мала:

| Причина | Почему hint слабо влияет на краулер |
| --- | --- |
| Batch, не «клик пользователя» | Нет сценария «сейчас пойду по ссылке» |
| Свой cache ресурсов | Не refetch’ят всё синхронно каждый раз |
| DNS/connect у Google другой | Их сеть уже «быстрая к DNS» |

Нюанс истории: ранний preload результатов пересекался с privacy (cookies / «меня видели в выдаче») и с идеей mcache без cookies — отдельная бурная тема.

**SEO-вывод:**

- как «технический сигнал ранжирования» эти link-hints почти не важны;
- как UX → retention / conversion → **вторичный** SEO-эффект — да, если измеряете поведение на сайте.

## Semantic HTML: важно ли Search?

Вопрос Martin’а: один `h1` + `article`/`section`/`nav` vs «просто абзацы и картинки» / много `h1`.

Позиция Gary по Search:

- заметной разницы обычно **нет**, пока нет совсем странного;
- «валидный HTML» как ranking boost нереалистичен (пропущенный `</span>` → invalid, для пользователя ноль изменений);
- споры «только один H1» vs «H1 на каждую секцию» для Search — скорее стилистика; визуально всё равно можно оформить CSS.

Semantic markup полезен для accessibility и людей/браузеров; для поисковиков — слабый рычаг.

## Практический чеклист

1. SEO-metadata (`canonical`, `robots`, `hreflang`, важные `link`/`meta`) — в **начальном HTML в `<head>`**.
2. Не ставьте в head то, что парсер воспримет как начало body (`<p>`, iframe из скрипта и т.п.) — проверите после исполнения JS.
3. Не полагайтесь на «валидатор зелёный = SEO ок»; смотрите на **где сигнал оказывается после parse/render**.
4. Избегайте mixed signals: один canonical в raw, другой после JS.
5. Prefetch/preload — для пользователей и конверсии, не как «магия для Googlebot».
6. Semantic HTML — делайте для людей/a11y, не ждите прямого ranking boost.

## Кратко

| Тема | Вывод |
| --- | --- |
| Regex-парсинг HTML | Не работает на реальном вебе |
| W3C validity | Почти не критична сама по себе |
| Закрытие `<head>` | Браузер (и Search) закрывают head на «не-metadata» |
| Metadata в body | Плохая идея для search-сигналов |
| Performance hints | Сильно для UX, слабо как прямой SEO-сигнал |
| Semantic markup | Полезно людям; для Search — малый эффект |

Одна фраза: поисковик пытается вести себя как браузер при разборе HTML, поэтому «где оказался тег после parse» важнее, чем «я положил его в head в исходнике в Notepad».
