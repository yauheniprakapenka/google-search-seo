# Episode 108: Analysing Robots.txt at scale with HTTP Archive and BigQuery

Разбор выпуска *Search Off the Record* с Gary Illyes и Martin Splitt: как команда Google через HTTP Archive и BigQuery собрала статистику директив в `robots.txt` в масштабе веба — и почему «просто добавить тег в документацию» у них начинается с данных.

---

## Зачем вообще смотреть robots.txt «в масштабе»

В официальный репозиторий документации по `robots.txt` пришёл хороший pull request: добавить две новые директивы в список **unsupported tags** — чтобы Search Console мог сообщать, что тег распознан, но Google его не поддерживает.

Автор PR: username вроде `3x10^8`. Идея здравая. Но в Google стараются не делать такие вещи «на глаз»: сначала данные, потом решение.

John Mueller предложил расширить задачу: не добавлять один тег, а посмотреть **топ-10 / топ-15** реально встречающихся неподдерживаемых директив и задокументировать baseline по самым частым.

Дальше выяснилось неочевидное: публичного удобного корпуса `robots.txt` «под рукой» почти нет. Решение — **HTTP Archive**.

---

## Что такое HTTP Archive (и Web Almanac)

HTTP Archive много лет собирает данные по большому числу страниц, чтобы отвечать на вопросы вида:

- на каком языке сайты;
- мобильны ли они;
- используют ли HTTPS / canonical;
- как выглядят performance и Core Web Vitals.

Это не «просто скачать HTML». Нужны:

1. **Crawl / fetch** страниц из известного списка URL.
2. **Render в браузере** — иначе не получить CWV, unused CSS, Lighthouse и поведение JS.

Исторически список URL берётся из **Chrome UX Report** (CrUX): агрегированные UX-метрики реальных пользователей Chrome. Масштаб — порядка **~16+ млн** URL.

| Фокус | Смысл |
| --- | --- |
| Home pages | Классический фокус: главная обычно «лицо» сайта |
| Secondary pages | В последние годы добавили внутренние/вторичные страницы для сравнения |

Технически прогон часто идёт через инфраструктуру вроде **WebPageTest**: URL открывают в реальном браузере на сервере. Отсюда данные, которых не даст `curl`/`wget`.

Раз в год сообщество пишет **Web Almanac**: задаёт вопросы к большому датасету и публикует главы (в том числе SEO).

---

## Два этапа работы с данными

| Этап | Что происходит |
| --- | --- |
| 1. Сбор | URL из CrUX → прогон в браузере → метрики (Lighthouse, performance, custom JS) |
| 2. Анализ | Данные в **BigQuery** → SQL-запросы → агрегаты, перцентили, распределения |

Default-метрики уже есть «из коробки» (например, LCP из Lighthouse). Всё, чего нет в стандартных инструментах, собирают через **custom metrics** — свой JavaScript, который выполняется после загрузки страницы в тестовом браузере.

Примеры custom metrics:

- какие элементы лежат в `<head>`;
- charset в meta;
- разбор `robots.txt` и список встреченных правил.

---

## Большой сюрприз: robots.txt в датасетах почти не было

Первая попытка Gary — сразу лезть в BigQuery — закончилась дорого: один тяжёлый запрос → счёт на **сотни долларов**. (У команды даже есть внутренний опыт/пост Danielle Waisberg про то, как не жечь деньги на BigQuery.)

Хуже: типичные датасеты HTTP Archive **не содержат** сами `robots.txt` — их почти никто специально не запрашивал в нужном виде. Деньги потрачены, корпуса нет.

Правильный путь подсказал Barry Pollard: писать custom metric в GitHub-репозитории HTTP Archive и собирать нужное на следующем прогоне.

---

## Что сделали с custom metric для robots.txt

В репозитории custom metrics уже был JS, который считал **заранее зашитый** набор правил (`noindex`, `noarchive`, `crawl-delay` и т.п.).

Команде нужно было обратное: узнать **все** директивы, которые люди реально пишут, а не только известные.

Решение:

1. Взять существующий extractor.
2. Перевернуть логику: парсить всё, что похоже на `key: value`.
3. Собрать отзывы Barry и community в GitHub.
4. Успеть смержить код до ближайшего прогона (submission ~3 февраля → данные попали в February dataset).

### Как парсили

Цель — примерно имитировать поведение C++ parser’а Google: идти **построчно**, вытаскивать всё, что выглядит как правило (`ключ: значение`).

Regex для этого написал AI («toaster») — «монстр» на строке ~58. Его много раз тестировали и даже прогоняли через fuzzer; на практике не ломался.

На выходе в custom metrics уходит JSON: извлечённые правила + доп. поля вроде raw byte size файла.

## Что показало распределение правил

Распределение директив — **очень крутой спад** после популярных:

1. `User-agent`
2. `Allow` / `Disallow`
3. Дальше — резкий обвал (даже на log scale)

Также всплывает много мусора:

- HTML error-страницы вместо `robots.txt` (с CSS: `padding`, `img`, `color`, `width`…);
- опечатки в `Disallow` и других директивах;
- «весёлый» текстовый шум в битых файлах.

Часть этого можно отфильтровать жёстче (например, требовать HTTP 200 и не-HTML content-type). Но нюанс: Google технически умеет вытаскивать правила и из ответов, похожих на HTML, если статус 200 — поэтому «строгий» фильтр для research и production-поведение парсера Google — не одно и то же.

Данные теперь в latest crawl → **custom records** в BigQuery; их можно достать самостоятельно.

## Связь с Web Almanac (SEO chapter)

Такой сбор может усилить SEO-главу Almanac: больше фактов, меньше догадок.

Уже в существующих разборах Almanac по `robots.txt` (по их crawl set) встречались ориентиры вроде:

| Наблюдение | Порядок цифр из обсуждения |
| --- | --- |
| HTTP 200 | ~84.9% |
| HTTP 404 | ~13% (в разговоре звучало как заметная доля 404) |
| 3xx / 5xx / timeout | обычно <1% |
| Размер файла | чаще всего 0–100 KB |
| `User-agent: *` | очень распространён |
| Упоминания ботов | AdsBot-Google заметнее, чем узкий `Googlebot` (~6.2% vs ~9.8% для AdsBot-Google в прошлом срезе) |

Точные проценты зависят от года и выборки — смотрите актуальную SEO-главу Web Almanac.

## Практические выводы

1. **Документацию unsupported-директив лучше строить от частоты в вебе**, а не от единичного PR.
2. HTTP Archive + BigQuery — рабочий путь для SEO-research в масштабе, но:
   - датасеты огромные;
   - необдуманный SQL дорого стоит;
   - нужных полей может не быть, пока не напишете custom metric.
3. Custom metrics — способ добавить в Almanac/HTTP Archive то, чего нет в Lighthouse «из коробки».
4. Реальный `robots.txt` в вебе шумный: опечатки, HTML вместо текста, редкие экзотические директивы с длинным хвостом.
5. Если исследуете директивы — смотрите распределение: после Allow/Disallow/User-agent почти всё становится long-tail.

---

## Кратко

Эпизод — не про «как написать robots.txt», а про data-driven подход Google: чтобы расширить список неподдерживаемых тегов, команда подняла корпус через HTTP Archive, дописала custom metric, дождалась прогона и разобрала BigQuery.

Главный урок для SEO и исследователей: масштабный анализ веба возможен, но инфраструктура (CrUX → WebPageTest → custom JS → BigQuery) важнее, чем один красивый SQL. А `robots.txt` в дикой природе гораздо грязнее, чем в учебниках.
