# Episode 99: Optimizing login-page content for Google Search

Разбор выпуска *Search Off the Record* с Martin Splitt и John Mueller: нужен ли SEO контенту за логином, чем paywall отличается от «просто login», почему generic login-страница убивает выдачу и как проверить свой сервис глазами незалогиненного пользователя.

---

## «У нас всё за логином — SEO не нужен»

Короткий ответ: **it depends**.

| Цель | Нужно ли думать про SEO |
| --- | --- |
| Совсем не важно, что видно в Search; контент закрыт | Можно почти не заморачиваться |
| Хотите, чтобы сервис/бренд находили, но тело контента закрыто | Да — настройте, **что** видит Google и пользователь без логина |
| Хотите индексировать статьи за paywall/login | Да — модель paywalled content + structured data |

---

## Две разные модели

### 1. Paywalled / limited content (хотите в индексе)

Контент есть, но доступ ограничен: подписка, логин, meter (N бесплатных страниц), иногда «посмотрите рекламу / видео» перед показом.

Как обычно делают:

1. Распознать Googlebot (или иначе отдать полный контент для индексации — по доке Google).
2. Отдать Google содержимое, которое хотите индексировать.
3. Пометить страницу **paywalled structured data**, чтобы было ясно: пользователям контент не всегда полностью доступен.

Structured data уместна и при A/B порогах («кому-то 5 страниц бесплатно, кому-то всё»).

**Важно по UX/доступности:** не грузите paywalled текст в DOM и не «включайте» его JS’ом так, что screen reader зачитает скрытое. Контент должен реально появляться только когда доступ разрешён.

Документация Google по paywalled content — отправная точка.

### 2. По-настоящему private (не хотите в индексе)

Приватный форум, личные URL (Drive-like), «свой» spreadsheet в браузере, закрытый сервис по подписке без показа в Search.

Здесь не «отдайте Google полный текст». Нужно решить: что происходит при заходе на private URL без авторизации — и что попадает в индекс.

---

## Как делают крупные сервисы (пример Search Console)

Паттерн лучше, чем голый login:

1. Есть **публичные marketing pages**.
2. Заход на private URL без логина → **redirect на marketing page** с кнопкой/ссылкой «Sign in».
3. В Search находятся понятные страницы сервиса, а не чужой `…/performance` с формой логина.
4. Случайные шаринги private URL не превращают выдачу в «Sign in here».

Итог для SEO: индексируется осмысленный публичный контент; private URL не становятся главной витриной бренда.

---

## Главная ловушка: одинаковый login на всех private URL

Если любой private URL показывает одну и ту же страницу «username / password» без контекста:

- Google видит массу дублей;
- схлопывает их;
- в индексе доминирует **login page**;
- по запросу про сервис пользователь находит в основном «войдите» — плохой опыт.

### Что делать

| Ситуация | Подход |
| --- | --- |
| Хотите findability сервиса | Контекст на login / marketing page: что за сервис, зачем он |
| Несколько продуктов на одном login | Чуть разные тексты (Docs vs Sheets), чтобы выдача различала |
| Контент private, Google не должен его видеть | **Не** отдавайте полный private-контент боту «для SEO» |

---

## robots.txt vs noindex для private

Закрыть private-раздел только `Disallow` в robots.txt — **плохая идея**, если URL уже «известны»:

- содержимое не увидят, но URL могут всё равно попасть в индекс (ссылки, `site:`);
- в выдаче — «пустые» URL «попробуйте сами»;
- ещё хуже, если в URL есть **email / username** (утечка через индекс).

Для private предпочтительнее:

- `noindex` на ответе **или**
- redirect на login/marketing page;
- не светить PII в URL;
- не полагаться на «robots.txt = не проиндексируется».

Хеши в URL чуть безопаснее имён пользователей, но privacy всё равно не «решена» одним хешем.

---

## Нужно ли индексировать сам login

Снова зависит от продукта:

| Тип | Login в индексе |
| --- | --- |
| Публичный продукт (SaaS, Drive-like) | Часто да — но с контекстом / через marketing pages |
| Внутренний intranet только для сотрудников | Обычно **нет**: error / server-side auth / `noindex` на login |

Intranet’ы иногда случайно индексируются — обычно нежелательно.

Redirect vs inline login — чаще **техническое/security** решение (cookies, `login.yourdomain.com`), не чисто SEO.

Даже e-commerce: URL «мои заказы» / аккаунт могут залинковать → Search попробует проиндексировать. Важно, что увидит незалогиненный пользователь.

Отдельный риск публичных Docs: сделали public → проиндексировали → снова private/удалили → выдача «отстаёт», пока не выпадут.

## Топ-совет выпуска: проверьте себя в Incognito

1. Откройте **incognito** (не залогинены).
2. Ищите бренд / имя сервиса.
3. Откройте топ результатов.
4. Если сверху голый login без объяснений — улучшайте.
5. Если сверху нормальный marketing/объясняющий контент — ок.

Для узких зон (orders, account):

- ищите по паттерну URL или характерным словам;
- смотрите, не «пугает» ли login без контекста;
- прогоните URL через **URL Inspection** в Search Console: что видит Google vs что видите вы.

Дальше: откуда URL, что отдаётся боту, план правок (marketing redirect, текст на login, `noindex`, убрать PII из URL).

---

## Практический чеклист

1. Решите: контент должен быть в индексе или нет.
2. В индексе + ограниченный доступ → paywall model + structured data; не прячьте текст в DOM для screen reader.
3. Private → `noindex` / redirect; **не** только robots.txt.
4. Не делайте один пустой login на все private URL — добавляйте контекст или marketing landing.
5. Не светите email/username в URL.
6. Регулярно смотрите выдачу бренда глазами незалогиненного пользователя.

---

## Кратко

Контент за логином не отменяет SEO — меняет вопрос: **что** должно находиться в Search. Paywall ≠ «спрятать от всех включая Google». Private ≠ «закрыть robots.txt и забыть». Самый частый провал — дублирующийся пустой login, который становится лицом сервиса в выдаче. Лечится marketing pages / контекстом на login и проверкой в Incognito.
