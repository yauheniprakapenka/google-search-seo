# Episode 107: Are websites getting “fat”? Page weight, HTML size & Googlebot limits explained

Разбор выпуска *Search Off the Record* с Gary Illyes и Martin Splitt: растут ли страницы, что вообще значит «page weight», где проходит граница «нормально / уже плохо» и как к размеру смотрит Googlebot.

---

## Сайт «жирный» — вопрос почти бессмысленный

Стартовый вопрос выпуска: *are websites getting fat?*

Gary сразу режет формулировку:

- в контексте **сайта целиком** «жирность» почти ничего не значит;
- в контексте **отдельной страницы** — да, размер можно определить и обсуждать.

Итоговая договорённость в конце: вопрос про website fat бессмысленный; корректнее спрашивать — **становятся ли web pages больше**. Ответ: **да**.

---

## Что такое page size / page weight

Одного «истинного» определения нет. Разные люди имеют в виду разное:

| Что считают | Пример смысла |
| --- | --- |
| Raw bytes HTML документа | Только parent HTML по URL |
| Transfer size «на диск пользователя» | HTML + CSS/JS + media, которые нужно скачать, чтобы увидеть страницу |
| То, что идёт по сети | С учётом сжатия (gzip/brotli) — меньше, чем uncompressed на диске |
| То, что занимает место на устройстве | После распаковки; важно при нехватке storage |

Web Almanac определяет page weight примерно так: **общий объём данных (KB/MB), который пользователь должен скачать, чтобы увидеть конкретную страницу**.

Цифры из Web Almanac 2025 (median mobile home page):

| Год | Median page weight |
| --- | --- |
| 2015 | ~845 KB |
| July 2025 | ~2.3 MB |

Рост примерно в **3 раза**: с «чуть больше половины дискеты» до «почти двух» (1.44 MB floppy как мем-референс выпуска).

Для сложных веб-приложений (условно «AutoCAD в браузере») рост ожидаем. На медиане — обычные сайты, и 2.3 MB уже ощутимо.

## HTML сам по себе тоже может быть огромным

Не только картинки и бандлы. Пример из выпуска — single-page HTML Living Standard (WHATWG):

- ~**14–15 MB** HTML почти без «красивой» обвязки — плотный текст + минимальная разметка;
- загрузка на быстром канале может занимать десятки секунд;
- Print to PDF в Chrome у Martin’а выходил ~96 MB; официальный PDF спеки — порядка ~15 MB.

Другая крайность в дикой природе: **inline images** (data URI прямо в HTML), чтобы сэкономить отдельный request — и HTML раздувается до десятков мегабайт (звучали кейсы ~50 MB).

Отсюда спорный вопрос:

> 15 MB почти чистого полезного контента — ок?  
> А 5 MB, из которых почти нет пользовательского текста, а сплошной markup / metadata — хуже?

Однозначного ответа нет. Появляется ratio **content vs markup**, и ещё сложнее: metadata для машин, регуляторики, лицензий — полезна, но не для глаза пользователя.

## Googlebot: лимит на fetch по URL

С точки зрения Search важнее не «вес сайта», а **сколько raw bytes Googlebot забирает с конкретного URL**.

По формулировке из выпуска (документация crawlers / Googlebot):

- по умолчанию fetch **~15 MB raw bytes** с конкретного URL, затем остановка;
- лимит **per URL**;
- ресурсы, на которые ссылается HTML, живут **своими** лимитами.

Для пользователя «15 MB на URL» часто нерелевантен: ему нужен документ целиком. Для краулера и индексации — это как раз рабочая рамка.

> Практический намёк: тяжёлый parent HTML (гигантские меню, inline-ассеты, огромный JSON-LD) бьёт именно в этот бюджет раньше, чем «красивый» вес всей страницы с картинками.

## Когда размер ещё важен (даже при 10 Gbit / 5G)

У Gary и Martin дома — гигабитный/10-gigabit мир, где bloat почти не чувствуется. Но:

- в travel / weaker networks «5G» на вышке может оказаться слабым каналом;
- metered satellite (кейс Antarctica: ~100 MB за заметные деньги) превращает тяжёлые страницы и соцприложения в проблему за минуты;
- паркинги, бункеры, плохой mobile reception — даже в «богатых» странах;
- нехватка storage на телефоне: compression помогает transfer time, но не месту на диске.

Гипотеза Martin’а: за последние годы рост transfer size на медиане обгонял рост типичных mobile speeds. Точных цифр в выпуске нет — как ощущение из наблюдений.

Смягчают боль:

| Механизм | Что даёт |
| --- | --- |
| Caching | Первый визит болезненный; reload HTML Spec не качает 15 MB снова |
| Transport compression | Меньше по проводу; на диске/у краулера после decode всё равно полный объём |
| Lazy loading | Тяжёлые image не грузятся, пока не в viewport |

Reader mode UX улучшает, но с loading почти не помогает: ресурсы всё равно нужно сначала получить, а «магия» — локально. На HTML Spec reader mode у Martin’а даже уронил вкладку.

## Structured data, metadata и идея «отделить машины от людей»

Gary поднимает давний конфликт:

- исторически (в т.ч. позиция в духе Sergey Brin) машины должны понимать текст сами;
- structured data — специально **для машин**, пользователь его не видит;
- при агрессивном наслаивании разметки страница пухнет без видимой пользы человеку, но может помочь трафику через rich results.

На IETF обсуждали идею отделять metadata от user-visible content — например, trusted clients получают machine-readable endpoint (`?output=json-ld` и т.п.). В идеале звучит разумно; на практике утопия:

- не все играют честно;
- spam в Search измеряется миллиардами URL/день;
- отдельный «удобный» machine channel, скорее всего, **усилит** спам для поисковиков и LLM.

Урок из mobile-first: разные URL / разные представления часто **ломают parity** (контент, ссылки, navigation, hreflang, link elements). Даже «просто mobile vs desktop» уже был болью. Масштабировать это на «HTML для людей / JSON для машин» опасно.

---

## Нужно ли что-то делать

Да — не как моральный долг «перед Google», а потому что:

- быстрее страницы обычно лучше retention и conversion;
- size влияет на network time и CPU parse/render;
- тяжёлые ассеты отрезают пользователей со слабым каналом и малым storage.

Мелкие практики из выпуска:

- не отдавать смартфону 5 MB / 59 MP картинку «потому что так снял»;
- у Google на developer docs есть linter: image **> 1 MB** блокирует submit;
- на скриншотах для доков часто разницу между сильно сжатым и «тяжёлым» глазом почти не видно — особенно если это не fine art.

Фикс «всего интернета» — тема на отдельный выпуск. Но каждый лишний мегабайт на критическом пути обычно вредит и пользователям, и краулингу.

## Кратко

| Вопрос | Ответ выпуска |
| --- | --- |
| Сайты «жиреют»? | Формулировка слабая; смотрите **страницы** |
| Страницы стали больше? | Да (~845 KB → ~2.3 MB median mobile home, 2015→2025) |
| Есть одно определение page size? | Нет: HTML / total download / wire / on-disk |
| Важен ли размер? | Зависит от контекста сети и устройства; в медиане — да |
| Лимит Googlebot | ~**15 MB raw bytes на URL**, ресурсы — отдельно |
| Что делать? | Резать bloat, жать media, кэш, lazy-load; не путать «полезно машине» с «нужно пользователю» |

Одна фраза: страницы реально стали тяжелее, быстрый интернет не отменяет проблему для всех, а для Search критичен размер **конкретного HTML/URL**, а не «вес сайта» в целом.
