# Episode 105: Google crawlers behind the scenes

Разбор выпуска *Search Off the Record* (Search Relations + Gary Illyes): почему «Googlebot» — не одна программа, как устроена внутренняя crawling-инфраструктура, чем crawler отличается от fetcher и какие лимиты реально стоят на fetch.

---

## Googlebot — не `.exe` и не вся инфраструктура

Люди часто говорят о Googlebot как о живом существе или одном бинарнике. Реальность другая.

Имя **Googlebot** исторически «залипло» с ранних 2000-х, когда продуктов и краулеров было мало. Потом появились AdWords и другие продукты → больше клиентов, которым нужно ходить в интернет → больше named crawlers. Называть всю crawling-инфраструктуру «Googlebot» стало **неточно**.

Коротко:

| Миф | Как на самом деле |
| --- | --- |
| Googlebot = вся система краулинга Google | Инфраструктура — отдельный внутренний сервис (в выпуске шуточно «Jack») |
| Googlebot — программа, которую «запускают» | Googlebot — **один из клиентов** этого сервиса |
| Один краулер на всё | Много команд вызывают общий SaaS-like fetch layer |

---

## Инфраструктура как внутренний SaaS

Внутренний crawling service:

- существует почти с рождения Google (раньше ближе к «wget на чужой машине инженера»);
- со временем переархитектурили под вызовы от многих команд;
- по сути делает одно: **fetch с интернета, не ломая интернет**, если сайт/ограничения позволяют.

Модель вызова:

1. Команда/продукт передаёт конфигурацию (URL или поток URL + параметры).
2. Сервис ходит наружу.
3. Клиент получает HTTP response: headers, body, metadata.

Параметры вызова (часть можно опустить — есть defaults):

- timeout / сколько ждать байты;
- User-Agent;
- robots.txt product token (каким правилам подчиняться);
- другие fetch-настройки.

Googlebot в этой схеме — **caller** (клиент SaaS), а не «сама платформа».

## Crawler vs fetcher

| | Crawler | Fetcher |
| --- | --- | --- |
| Режим | Batch / непрерывный поток URL | Один URL за раз |
| Список URL | Да, постоянный stream | Нет — только individual URL |
| Триггер | «Когда будет время / capacity» | Обычно **user-controlled**: кто-то ждёт ответ (кнопка → результат) |
| IP ranges | Могут отличаться | Могут отличаться |
| Инфраструктура | Тот же слой, другой режим работы | Тот же слой |

Документируют не всех. На [developers.google.com/crawlers](https://developers.google.com/crawlers) real estate ограничен: в списке major crawlers / special crawlers / fetchers. Мелкие проекты с низкой нагрузкой часто **не** попадают в публичную доку.

Внутренний триггер для документации: мониторинг + SQL-алерты по порогу fetches/day → bug «новый крупный crawler» → разбор свойств и команды.

Побочный эффект мониторинга: ловят «зомби»-джобы после sunset проектов (был кейс: команда думала, что краулер выключен два года назад, а job продолжал fetch’ить). Сейчас такие случаи редки — utility checks жёстче.

## Кэш, reuse и «не ходить дважды»

Внутри агрессивный caching **поверх** обычного HTTP caching.

Пример логики: если Google News забрал URL 10 секунд назад, web search может получить **копию**, а не идти в интернет снова.

Нюанс: политики reuse между продуктами разные. Не всё, что сходили для web search, можно переиспользовать в AdWords (и наоборот).

---

## Geo-blocking: не надейтесь, что «подстроятся»

Типичные egress IP Google (часто пулы вроде `66.x`) геоассоциированы с **US / Mountain View**. Это прямо отражено в документации: обычно краулят «из США».

Если сайт режет не-US трафик:

- вероятен 403 / timeout / drop на роутере без ответа;
- иногда инфраструктура может **lease** IP из пула с другой country-меткой;
- такие egress **не** рассчитаны на high-capacity crawl для всех стран → используют редко и frugally, чаще когда utility контента очень высока.

Практический вывод выпуска:

> Не рассчитывайте на geo-bypass. Хотите стабильно быть crawlable для Google — не режьте типичные Google IP по стране.

## «Please don’t break the internet»

Именно ради этого и существует центральный слой.

Инженер **не** должен с datacenter-машины открыть сокет и качать сайт на 10 Gbit/s напрямую. Прямой egress с серверов обычно закрыт; наружу — через fetch/crawler endpoints.

На уровне инфраструктуры:

- throttle при деградации сайта (растёт connection time → замедление);
- на **503** — ещё сильнее slowdown (сервер, скорее всего, перегружен);
- **403 / 404** сами по себе не сигнал «сайт умирает» — это client/URL-ошибки, не повод автоматически душить crawl так же, как 503.

Команды не контролируют этот safety-слой полностью — и это плюс.

## Лимиты размера: 15 MB default, у Search — жёстче

| Уровень | Лимит (из выпуска) |
| --- | --- |
| Default инфраструктуры | **~15 MB** raw bytes на fetch, затем stop |
| Google Search (в основном) | Override до **~2 MB** |
| PDF (пример порядка) | Выше, в разговоре звучало ~**64 MB** (смотрите актуальную доку) |
| Images | Обычно допускают больше 2 MB — иначе многие картинки бессмысленны |

Как работает 15 MB: идёт приём байтов → внутренний счётчик → на пороге приём останавливают (закрывают ли TCP сразу — Gary не уверен; смысл — «хватит»).

Почему у Search 2 MB на HTML: огромные one-pagers (HTML Living Standard ~14 MB) бесполезны для пайплайна целиком; выгоднее брать отдельные страницы спеки. Тяжёлый PDF целиком → convert → process перегружает систему.

Конфиг может меняться **на уровне запроса/проекта**, не только «Googlebot всегда одинаковый». Для срочного indexing теоретически лимит могут ещё урезать (в выпуске как гипотеза — даже до ~1 MB).

Актуальные цифры — в официальной документации crawlers / Googlebot fetch limits.

## Картинка целиком

```text
[ Search / News / Ads / другие продукты ]
              │
▼ API call (UA, robots token, timeouts, limits…)
     [ Внутренний crawling SaaS ]
              │
cache? throttle? robots? size limit?
              ▼
     интернет / ваш сайт
```

Googlebot — один из клиентов этой схемы, не «весь Google».

---

## Кратко

1. Crawling в Google — **внутренний SaaS**, не монолитный Googlebot.exe.
2. Googlebot = named client + его конфигурация вызовов.
3. Crawler = batch/stream; fetcher = single URL, обычно с человеком в конце.
4. Документируют крупных; мелких слишком много для одной HTML-страницы доков.
5. Есть внутренний cache и разные политики reuse между продуктами.
6. Geo-block по стране для Google — плохая идея, если нужна стабильная индексация.
7. Safety и throttle — на infrastructure level; default **15 MB**, у web Search чаще **2 MB** на HTML (с исключениями вроде PDF/images).

Если держать в голове модель «сервис с параметрами», разные user-agent’ы, лимиты и поведение перестают казаться магией одного бота.
